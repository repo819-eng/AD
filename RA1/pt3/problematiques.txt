Problematicas de los ficheros binarios y la serializacion

1. si cambias la clase Videojoc despues de guardar datos (por ejemplo añadir un atributo o cambiar un tipo) el fichero antiguo puede dejar de funcionar y salta una InvalidClassException. por eso se pone el serialVersionUID, porque si no java calcula uno y con cualquier cambio ya no coincide

2. es inseguro hacer readObject de ficheros que no sabes de donde vienen porque java crea los objetos que hay dentro y se puede llegar a ejecutar codigo que no quieres

3. no se puede leer con un editor de texto como el bloc de notas, salen simbolos raros. y solo lo puede leer java, si quieres abrir el fichero con python o php no funciona

4. si haces append al fichero con un ObjectOutputStream nuevo cada vez se pone una cabecera nueva en medio y despues al leer da StreamCorruptedException. para evitarlo yo guardo toda la lista entera de golpe

5. no hay manera facil de saber cuando se acaba el fichero, available() no sirve bien y se tiene que hacer con EOFException

6. todas las clases que guardas tienen que ser Serializable sino da NotSerializableException. si un atributo no lo quieres guardar se pone transient

7. si el programa peta mientras esta escribiendo el fichero se puede quedar corrupto y pierdes todos los datos

En resumen para una practica pequeña va bien porque es facil pero para una aplicacion de verdad es mejor usar json o una base de datosl és millor fer servir JSON o una base de dades.
